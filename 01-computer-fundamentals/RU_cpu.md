**CPU - как устроен и как работает процессор**

Это заметки для понимания того, что вообще происходит "внутри" компьютера, когда выполняется программа. Идея — объяснить не просто "что это", а почему это так устроено и как это работает вместе

-------------------------------------------------------------------------------------------

1. Что такое CPU и зачем он нужен

CPU (Central Processing Unit) — это "мозг" компьютера, но точнее будет сказать: это устройство, которое умеет делать только одну вещь — выполнять простые инструкции одну за другой, очень-очень быстро.
Когда ты пишешь программу на любом языке, в итоге она превращается в длинный список крошечных команд вроде "сложи эти два числа" или "перейди к следующей строке кода". CPU не знает, что такое Python или JavaScript — он видит только эти элементарные команды.

Путь программы такой:
Программа (код) → компилятор/интерпретатор → машинные инструкции → CPU выполняет их → результат

Пример: у тебя есть код A + B. CPU получает инструкцию вроде "сложить значение в регистре A со значением в регистре B", выполняет её за один шаг и кладёт результат туда, куда нужно.

Важно понимать: CPU не "думает" в человеческом смысле. Он просто механически исполняет инструкции — но делает это миллиарды раз в секунду, и из этого простого повторения рождается всё — от игр до операционных систем.

---------------------------------------------------------------------------------------------

2. Четыре типа операций, которые умеет делать CPU

Все, что делает CPU, сводится всего к четырём категориям действий. Это как алфавит — из этих простых "букв" собирается вообще любая программа.

Арифметические операции - это математика: сложение, вычитание, умножение, сравнение чисел.

5 + 3
A == B
Логические операции

Это побитовая/булева логика — операции, которые работают не с "числами" в обычном смысле, а с битами (0 и 1).

AND, OR, XOR

Например, эти операции используются, чтобы проверять условия ("оба ли значения истинны", "хотя бы одно" и т.д.), а также для битовых манипуляций в низкоуровневом программировании.

Перемещение данных

CPU постоянно перекладывает данные туда-сюда: из памяти в регистр, из одного регистра в другой, обратно в память.

LOAD  — забрать данные из памяти
STORE — положить данные обратно в память
MOV   — переместить данные между регистрами

Почему это отдельная категория? Потому что сами по себе данные не появляются там, где нужны — их сначала нужно физически "принести" туда, где CPU может с ними работать (в регистры).

Управление выполнением программы

Это то, что решает какая инструкция будет выполнена следующей. Без этого программа бы просто шла по прямой линии сверху вниз и не могла бы иметь циклы, условия (if), вызовы функций.

JUMP — перейти к другой инструкции
CALL — вызвать функцию
RET  — вернуться из функции

Пример того, как эти 4 типа работают вместе (упрощённо, псевдокод):

LOAD    — загружаем число из памяти в регистр
ADD     — складываем два числа
COMPARE — сравниваем результат с чем-то
JUMP    — если условие выполнено — прыгаем в другое место программы
STORE   — сохраняем итоговый результат обратно в память

Это грубый набросок реального цикла работы CPU. В настоящих архитектурах команды называются иначе (в x86-64 это, например, MOV, ADD, CMP, JMP), но суть та же — это просто "глаголы", из которых строится абсолютно любая программа, какой бы сложной она ни казалась снаружи.

3. ISA — общий "язык", на котором CPU понимает команды

ISA (Instruction Set Architecture) — это набор правил и конкретных инструкций, которые данный процессор умеет выполнять. Это как алфавит и грамматика конкретного языка — CPU понимает только те "слова", которые заложены в его ISA.

Разные семейства процессоров используют разные ISA, и они не совместимы между собой напрямую — инструкции, написанные для одной архитектуры, не будут работать на другой без перевода (эмуляции или перекомпиляции).

Две главные архитектуры сегодня:

Архитектура	Где используется
x86-64 (Intel, AMD)	Windows PC, Linux-серверы, дата-центры
ARM64 / AArch64	Смартфоны, Apple Silicon (M1/M2/M3...), Raspberry Pi, много облачных серверов
Intel Core     → x86-64
AMD Ryzen      → x86-64
Apple M-series → ARM64

Именно поэтому, например, программа, скомпилированная для Intel Mac, не запустится напрямую на Apple Silicon Mac без специального "переводчика" (как Rosetta у Apple) — это разные ISA, разные "языки" машинных инструкций.

4. Ядра и потоки — как CPU выполняет несколько вещей "одновременно"
Core (ядро)

Ядро — это, по сути, отдельный самостоятельный "мини-процессор" внутри CPU, способный независимо выполнять инструкции. Раньше процессоры были одноядерными — сейчас практически все современные CPU содержат несколько ядер.

Логика простая: больше ядер — больше задач может выполняться по-настоящему параллельно (а не по очереди, как приходилось бы с одним ядром).

Но важная оговорка: 8 ядер — это НЕ автоматически "в 8 раз быстрее". Реальная производительность зависит от множества факторов:

характера самой задачи (можно ли её вообще разбить на параллельные куски)
тактовой частоты
IPC (сколько работы делается за один такт)
архитектуры процессора
размера и скорости кэша
скорости памяти
того, насколько программа вообще написана с расчётом на многопоточность

То есть ядра — это потенциал для параллелизма, а не гарантия ускорения.

Thread (поток)

Поток — это "виртуальная" линия выполнения внутри ядра. Некоторые процессоры умеют выполнять два потока на одном физическом ядре одновременно, разделяя его ресурсы.

Пример: "4 cores, 8 threads" означает, что каждое из 4 ядер поддерживает по 2 аппаратных потока.

Core 1 → Thread 1 + Thread 2
Core 2 → Thread 3 + Thread 4
Core 3 → Thread 5 + Thread 6
Core 4 → Thread 7 + Thread 8
У Intel эта технология называется Hyper-Threading
У AMD — SMT (Simultaneous Multithreading)

Важно понимать: два потока на одном ядре — это НЕ то же самое, что два полноценных физических ядра. Они делят между собой ресурсы одного ядра (например, ALU), поэтому прирост производительности от этого обычно заметно меньше, чем от реального добавления ещё одного ядра. Представь это как двух людей, которые делят один стол — они могут работать "параллельно", но всё равно иногда мешают друг другу, потому что ресурс (стол) один.

5. Тактовая частота (Clock speed) — "пульс" процессора

У CPU есть внутренний генератор тактовых импульсов — представь это как метроном, который непрерывно "тикает" с определённой скоростью. Каждый его "тик" называется тактом (clock cycle), и по каждому такту CPU синхронно продвигает свою работу на один шаг.

4.5 GHz означает: этот "метроном" делает примерно 4.5 миллиарда тиков в секунду.

Казалось бы — логично предположить, что 4.5 GHz = 4.5 миллиарда инструкций в секунду. Но это не так, и вот почему:

Одна инструкция может требовать нескольких тактов для выполнения (например, деление обычно "дороже" сложения)
Современные процессоры выполняют инструкции сложным, "конвейерным" способом — несколько инструкций могут находиться в разных стадиях выполнения одновременно ("в полёте")

Поэтому вводится понятие:

IPC (Instructions Per Cycle) — сколько инструкций в среднем CPU реально выполняет за один такт. Чем выше IPC при той же частоте, тем эффективнее архитектура процессора.

Именно поэтому сравнивать процессоры только по гигагерцам — ошибка. Процессор с 3.5 GHz и высоким IPC вполне может обгонять процессор с 4.5 GHz и низким IPC.

6. ALU — "калькулятор" внутри CPU

ALU (Arithmetic Logic Unit) — это конкретный блок внутри CPU, физически отвечающий за выполнение:

арифметических операций: +  −  *
логических операций: AND  OR  XOR
операций сравнения: <  >  ==

Когда инструкция требует что-то посчитать или сравнить — именно ALU выполняет эту работу. Всё остальное в CPU (управление, память, регистры) существует, по большому счёту, чтобы вовремя подать ALU нужные данные и забрать у него результат.

------------------------------------------------------------------------------------------------------

7. Control Unit — "дирижёр" процессора

Control Unit не выполняет вычисления сам — он координирует работу всех остальных частей CPU: решает, что нужно сделать с текущей инструкцией, и направляет данные туда, куда нужно (в ALU, в регистры, в память).

Instruction
   ↓
Control Unit  ("что нужно сделать с этим?")
   ↓
ALU / регистры / память

Пример:

Register A = 10
Register B = 20
Инструкция: ADD A, B

Control Unit видит инструкцию ADD, понимает, что нужно взять значения из регистров A и B, передать их в ALU, получить результат и записать его обратно.

Результат: A = 30

Почему используются именно регистры, а не сразу оперативная память? Потому что регистры находятся физически внутри самого CPU и работают на порядок быстрее, чем обращение к RAM. Это как разница между тем, чтобы взять инструмент со своего стола (регистр) или сходить за ним на склад (оперативная память).

-------------------------------------------------------------------------------------

8. Instruction Pointer — "закладка" в коде программы

Instruction Pointer (в x86-64 называется RIP) — это специальный регистр, который хранит адрес следующей инструкции, которую CPU должен выполнить.

Представь код программы как последовательность ячеек памяти:

Memory:
0x1000 → instruction A
0x1004 → instruction B
0x1008 → instruction C
             ↑
            RIP

Цикл работы предельно прост:

CPU смотрит, куда указывает RIP
Забирает инструкцию по этому адресу
Выполняет её
RIP автоматически сдвигается на следующую инструкцию (или "прыгает" в другое место, если это была инструкция перехода — JUMP)
Повторить

По сути, RIP — это "закладка", которая всегда показывает CPU, "на чём я остановился"

9. Stack Pointer — как CPU помнит, куда вернуться

Чтобы понять Stack Pointer, сначала нужно понять сам стек.

Что такое стек

Стек — это область памяти, работающая по принципу LIFO (Last In, First Out) — "последним пришёл, первым вышел". Самая понятная аналогия — стопка тарелок: ты можешь класть тарелку только сверху, и забирать тоже только сверху. Нельзя вытащить тарелку из середины стопки, не сняв всё, что лежит выше.

В x86-64 стек растёт вниз — то есть в сторону уменьшения адресов памяти (что немного контринтуитивно, но так исторически сложилось).

Что такое Stack Pointer

Stack Pointer (в x86-64 — RSP) — это регистр, который всегда хранит адрес текущей "вершины" стека, то есть указывает, где именно сейчас находится "верхняя тарелка".

Зачем вообще нужен стек

Стек используется, когда программа вызывает функции. И главная проблема, которую он решает — CPU должен помнить, куда вернуться после того, как функция закончит работу.

Представь цепочку вызовов:

function A()
    ↓ вызывает
function B()
    ↓ вызывает
function C()

Когда C() закончится — CPU должен вернуться обратно в B(), причём ровно в то место, откуда был вызов. А когда закончится B() — вернуться в A(). Стек — это то, что хранит "историю" этих вызовов, как хлебные крошки на пути.

Как это выглядит по шагам

Когда main() вызывает foo():

CPU кладёт на стек return address — адрес инструкции, на которую нужно будет вернуться после выполнения foo()
RSP сдвигается вниз (стек "растёт")
Внутри foo() могут появляться локальные переменные — они тоже кладутся на стек, RSP снова сдвигается
Когда foo() завершает работу — return address снимается со стека
Значение из return address записывается в RIP — и CPU буквально "прыгает" обратно в main(), туда, где вызов был сделан
RSP возвращается на то место, где был до вызова

Наглядно (стек растёт сверху вниз по адресам):

Высокий адрес
┌───────────────────────┐
│ return address          │  ← куда вернуться после foo()
├───────────────────────┤
│ локальные переменные foo │
├───────────────────────┤
│ ...                      │  ← сюда указывает RSP (вершина стека)
└───────────────────────┘
Низкий адрес
Почему это критически важно для безопасности

Return address — это по сути обычные данные в памяти, а не что-то "защищённое" магией. А значит, если программа неаккуратно записывает данные в буфер, лежащий на стеке (классический пример — использование функции вроде strcpy без проверки длины входных данных), и запись выходит за границы этого буфера — она может затереть return address.

Тогда при завершении функции CPU попытается "вернуться" не туда, куда должен был, а туда, куда записал атакующий. Это фундаментальная идея, лежащая в основе целого класса атак:

Термин	Объяснение
Buffer overflow	Переполнение буфера — запись данных за границы выделенной под них памяти
Memory corruption	Более широкий класс багов, связанных с повреждением памяти (buffer overflow — один из частных случаев)
ROP (Return-Oriented Programming)	Техника, при которой атакующий не внедряет новый код, а "склеивает" уже существующие в программе небольшие кусочки кода (gadgets), манипулируя чередой return-адресов на стеке
Exploit development	Разработка кода, который использует найденную уязвимость (например, memory corruption) для получения контроля над программой
Debugging	Процесс поиска причин ошибок в программе — часто с пошаговым выполнением кода и наблюдением за содержимым регистров и памяти в реальном времени
Malware analysis	Изучение вредоносных программ: как они устроены, что делают, как их обнаружить и обезвредить

Понимание стека и return address — это буквально фундамент, без которого невозможно осознанно заниматься reverse engineering, эксплойтами или анализом вредоносного ПО

10. Registers — рабочий стол CPU

Регистры — это крошечные, но невероятно быстрые ячейки памяти, расположенные физически внутри самого CPU (в отличие от оперативной памяти, которая находится отдельно и физически дальше).

Это "рабочий стол", на который CPU кладёт данные, с которыми работает прямо сейчас. Регистров немного (в отличие от гигабайт оперативной памяти), но обращение к ним происходит практически мгновенно по сравнению с обращением к RAM.

К регистрам общего назначения (для хранения произвольных данных) добавляются специальные регистры с конкретной ролью — например, уже знакомые нам RIP (указывает на следующую инструкцию) и RSP (указывает на вершину стека).

---------------------------------------------------------------------------------------------

11. Flags / Status register — "заметки" CPU о последней операции

Это ещё один специальный регистр, где CPU автоматически сохраняет информацию о результате последней выполненной операции — своего рода короткие "заметки на полях":

Был ли результат равен нулю?
Было ли переполнение (число вышло за допустимые пределы)?
Был ли результат отрицательным?

Зачем это нужно? Потому что именно на основе этих флагов работают условные переходы. Когда CPU выполняет что-то вроде "если A == B, перейти сюда" — на самом деле происходит так: сначала выполняется сравнение (COMPARE), результат которого выставляет флаги, а затем инструкция перехода (JUMP IF EQUAL) просто проверяет нужный флаг и решает, прыгать или нет.

12. CPU Cache — быстрая память "под рукой" у процессора
Зачем вообще нужен кэш

Мы уже выяснили: регистры — сверхбыстрые, но их мало. Оперативная память (RAM) — большая, но по меркам CPU очень медленная. Разница в скорости огромна: пока CPU ждёт данные из RAM, он может успеть выполнить сотни инструкций впустую.

Представь: ты работаешь за столом (регистры), но нужные тебе документы хранятся не на столе, а в архиве в другом здании (RAM). Каждый раз бегать в архив — это катастрофически медленно, даже если сам архив огромный и в нём есть всё что нужно.

Кэш — это как маленький шкаф рядом со столом, куда ты заранее переносишь документы, которые, скорее всего, понадобятся снова в ближайшее время. Он гораздо меньше архива, зато обращение к нему занимает секунды, а не походы через весь город.

Физически кэш — это тоже память, но она расположена гораздо ближе к ядрам CPU (иногда прямо внутри них) и сделана по более быстрой, но и более дорогой технологии, чем обычная RAM. Именно поэтому кэша всегда мало — мегабайты, а не гигабайты.

Уровни кэша: L1, L2, L3

Кэш обычно устроен в несколько уровней, от самого быстрого и маленького до более медленного и большого:

Уровень	Скорость	Размер	Расположение
L1	Самый быстрый	Самый маленький (обычно десятки КБ)	Свой у каждого ядра
L2	Быстрый	Побольше (сотни КБ – пара МБ)	Часто тоже свой у каждого ядра
L3	Медленнее, чем L1/L2, но всё равно намного быстрее RAM	Самый большой (несколько МБ – десятки МБ)	Обычно один общий на весь CPU (все ядра)

Логика простая — сначала CPU ищет данные в L1 (самое близкое и быстрое место). Не нашёл — идёт в L2. Не нашёл там — идёт в L3. И только если данных нет ни в одном уровне кэша, CPU обращается к RAM — что происходит значительно медленнее всего остального.

Cache hit и cache miss

Когда CPU находит нужные данные в кэше — это называется cache hit ("попадание в кэш"). Когда данных там нет и приходится идти в RAM — это cache miss ("промах").

Чем больше hit'ов и меньше miss'ов — тем быстрее в реальности работает программа, даже если тактовая частота и IPC одинаковые. Именно поэтому размер и эффективность кэша — один из ключевых факторов реальной производительности CPU, наравне с частотой и количеством ядер.

Откуда CPU знает, что положить в кэш

CPU не угадывает наугад — он опирается на два простых наблюдения о том, как обычно ведут себя программы:

Временная локальность (temporal locality): если какие-то данные использовались только что — велика вероятность, что они понадобятся снова очень скоро (например, переменная-счётчик в цикле).
Пространственная локальность (spatial locality): если CPU обратился к какому-то адресу памяти — высока вероятность, что скоро понадобятся и соседние адреса (например, элементы массива, лежащие подряд).

Поэтому, когда CPU забирает данные из RAM, он обычно забирает не одну ячейку, а сразу целый "кусок" памяти по соседству (это называется cache line) — в расчёте на то, что эти соседние данные тоже вот-вот понадобятся.

Почему это важно на практике

Именно из-за кэша два процессора с одинаковой частотой и количеством ядер могут показывать заметно разную реальную скорость — у того, чей кэш больше или эффективнее устроен, будет меньше "простоев" в ожидании данных из RAM.

Это же объясняет, почему то, как написан код, влияет на производительность не меньше, чем железо: если программа обращается к памяти предсказуемо и последовательно (например, проходит по массиву подряд) — она гораздо лучше "дружит" с кэшем, чем программа, которая скачет по памяти в случайном порядке.
